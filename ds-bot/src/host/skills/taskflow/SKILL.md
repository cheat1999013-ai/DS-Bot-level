# Taskflow

群聊中的任务流使用 DS Bot 自带的 SQLite 账本。`taskflow_*` 工具的返回结果是任务状态依据；群聊文字用于交流，不替代账本。

## 隐藏关键词检索（睡眠机制）

派发、提报结果、验收与心得节点自动得到一个仅在索引中的唯一关键词。关键词不出现在正文或群消息里。先用 `taskflow_memory_search` 按关键词片段或摘要检索当前群，取得精确关键词，再用 `taskflow_memory_open` 打开该节点原文。心得写入和合并只是提供节点内容，不能替代搜索与打开；跨群或私聊不能打开群节点。归档清理后打开同一关键词会明确提示原始明细已清理。

## 按群技能库和 Bot 等级

整个计划成功完成后才给执行 Bot 计分，按当前群、计划和 Bot 去重，每个执行 Bot 在同一计划最多一次；主理不因管理身份获奖。完成前为普通时加 0.1 级，达到优良后每计划加 0.01 级，精品继续按 0.01 级增长；单卡验收、失败和取消不新增奖励。未满 16 级普通，达到 16 级优良，达到 27 级精品，41 级及以上仍为精品。历史已获等级保留，不追溯降级。`taskflow_skill_level` 返回已计分计划数、当前等级和本群分档。十条同群同主题独立心得产生普通技能草稿，十份已审核普通技能产生优良草稿，十份已审核优良技能产生精品草稿。`taskflow_skill_candidates` 仅主理查看，`taskflow_skill_review` 做 Bot 审核；归纳正文时用 `taskflow_skill_consolidate` 请求群主人工审核，通过后才进入可检索技能库。草稿不会自动装备。成员用 `taskflow_skill_search` 搜本群已审核且符合等级的技能，拿 ID 后用 `taskflow_skill_open` 读取正文，精确打开也会再次核验等级和群归属。

## 技能文件、自动加载和共享库

主理应主动用 `taskflow_skill_insights` 分页检查本群历史汇总心得，按相同的适用前提、方法步骤和验证方式识别可复用经验，而不是要求文章题目或整篇复盘相似。选择十个不同计划，通过 `taskflow_skill_propose_method` 提交每条原文步骤和验证证据，先取得不占用来源的预览；逐条复核完整来源确为独立同方法后，以相同参数和预览返回的 `previewDigest` 再次调用，形成普通草稿。预览后来源变化须重新预览；不跨群、不重复占用来源，也不能把不相关方法凑足十条。随后仍需执行原有 Bot 和人工审核。

### 分类标签

主理在 `taskflow_skill_consolidate` 晋升技能时必须提交 `tags`，与准确正文一同人工审核。例如 `['设计-UI']` 自动补齐「设计」，还可使用「设计-网页」「设计-图像」「设计-电商图像」「代码-前端」「代码-后端」「代码-测试」等按真实用途扩展的细类；最多四级，用半角 `-` 连接。不同用途可赋多个标签，标签不替代原有群归属和 Bot 等级权限。执行者先用 `taskflow_skill_search({tags:['设计-UI'],query:'可选关键词'})` 找标签和摘要，再用 `taskflow_skill_open` 读取准确正文，不能凭标签猜正文。父类搜索涵盖子类，多个细类筛选需同时满足。历史技能无标签时显示待分类，仍可按正文搜索，不编造旧标签。

### 五天评分和精品保护

仅已批准的普通、优良技能从启用后的完整五天（120小时）开始参评，宿主定时检查到期并唤醒来源群当前主理。精品技能（技能自身 tier=premium，不是调用 Bot 的等级）不采用本评分制度，不会自动进入待遗忘或淘汰；不得给精品创建评分、提交旧评分请求或以零调用清理它。主理用 `taskflow_skill_score` 无参数取得待评分正文及固定统计窗口，再提交 `cycleId` 和六项 `ratings`。质量项为 `scope` 适用场景、`inputs` 输入与前提、`steps` 执行步骤、`validation` 输出与验收、`prevention` 错误预防、`boundaries` 使用边界；每项 `{score:0或0.5,evidence:'对应正文依据或缺失说明'}`，共3分。不得以技能标签、等级或自己的主观偏好冒充质量依据。

宿主独立核算调用频次2分：最近窗口0次=0分、1次=0.5分、2–3次=1分、4–6次=1.5分、7次及以上=2分。主动打开且成功返回正文才记录读取事件；工具读取按宿主可信 callId 去重，同任务内不同 callId 分别计次。通过 DSH 技能注册表读取正文也计入独立任务读取，同任务/会话/五天时间段的重复注册表读取去重。自动装配次数单列，不冒充实际调用或模型正确应用。共享的普通、优良技能由来源群主理评分，汇总所有获授权群的有效读取；共享不改变精品豁免。

普通、优良技能总分低于3第一次进入「待遗忘」，主理和执行者仍可搜索、打开、自动装配；下一独立五天周期仍低于3才淘汰。达到3（包含恰好3）恢复正常并清零连续低分。零调用的普通、优良技能仍评审，质量满分得3分，可保留。未完成有效质量评审只显示待评分，不能默认0分淘汰；长时间离线不连补多轮评分。

淘汰后停止本群及共享的所有新检索、读取和装配，删除仅由本插件生成且内容未被人工改动的发布文件；来源心得和评分审计保留，已有上级技能不被级联删除。遇人工文件或目录链接冲突须报告，不能强行覆盖或删除。不要重新发布已淘汰技能来绕过遗忘机制。

合并心得导出为插件数据目录 `library/groups/<群键>/insights/<计划键>/INSIGHT.md`，逐卡来源在旁边 `sources.json`。双审技能导出为 `library/groups/<群键>/skills/<技能名>/SKILL.md` 和 `provenance.json`。数据库是审核与权限依据，草稿不会成为可加载技能。

每次群 Bot 的模型请求，宿主自动加载本 taskflow 指引及最多三份按当前任务和职责排序的已审核技能正文；同群和等级权限每次重验，实际装配记录保存在 `knowledge.sqlite` 的 `skill_loads`。目录可发现不代表已加载，也不代表模型已经正确应用。其他合规技能可通过 `taskflow_skill_search` 和 `taskflow_skill_open` 按需读取。

主理可用 `taskflow_skill_publish` 申请跨群公开；宿主展示准确技能正文、来源标题与正文/验收摘录、完整来源内容摘要，并请求一次人工审批。批准同时绑定完整来源集合，等待期间来源正文、验收证据或来源集合变化会拒绝发布。批准后生成 `library/shared/skills/<技能名>/SKILL.md`，其他群的合规等级 Bot 才能检索、读取和自动加载；后续来源变化也会使跨群授权失效，须重新审批，未发布技能保持群内作用域。`taskflow_skill_unpublish` 撤回后停止新的跨群读取和装配。

## 主理人（群管理员）

1. 先用 `taskflow_members` 读取本群成员及职责。
2. 用 `taskflow_plan` 创建计划。卡片的 `member` 必须是群成员；只有必须等待前一张卡验收才可开始的工作才设置 `dependencies`。设置 `confirm` 或 `testRequiredCards`/`testChecks` 时，相应门禁会由宿主强制执行。
3. 用 `taskflow_dispatch` 派发就绪卡；消息通过 DS Bot 群聊原生 @成员转发。派发后结束当前回合，让成员执行。
4. 收到成员 `taskflow_submit` 后，用 `taskflow_results` 看真实结果和证据；按需用 `taskflow_verify` 运行配置的测试（每次执行前由用户批准准确命令与工作目录）。`taskflow_confirm` 会向用户发起针对当前结果和决定的审批，批准后才写入决定。最后用 `taskflow_accept` 逐卡验收。打回用 `taskflow_reject`，失败或不确定状态用 `taskflow_retry`。
5. 全卡验收后用 `taskflow_finish`。多阶段项目应先用 `group_goal` 登记整体目标。阶段计划结束后继续推进下一阶段，项目通过总验收并调用 `group_goal complete` 后再收集心得。成员用 `taskflow_sleep_note` 写真实心得，主理人用 `taskflow_sleep_pending` 核实完整性后用 `taskflow_sleep_consolidate` 汇总。计划无法继续时用 `taskflow_cancel` 写明原因。
6. 主理应结合群目标、已有指令和验收结果主动判断后续：结果是否满足用户的完整目标，是否需要其他成员继续执行，以及是否存在等待用户决定的阻塞。执行卡职责只约束该执行者，不自动取消主理的后续协调职责。现有计划完成但整体目标仍需后续时，调用 `taskflow_plans` 核对本群最近20个计划及 `autoFollowUpEnabled`，注意更早历史不在返回范围；若 `autoFollowUpEnabled` 为 false，不自动创建或派发后续计划。确需新计划时按群成员职责创建并派发，避免重复。新计划可能改变当前指针，收取或汇总旧计划的心得时必须显式传入旧 `planId`。没有需要继续的工作或素材不足时说明判断依据；不能仅因收到结果或结束一张卡就宣称整体目标完成。严格遵守用户明确限定的任务边界、审批与未知送达约束。

## 执行成员

收到 `@你 [Taskflow 计划ID/卡片ID]` 后执行该卡任务。完成时用 `taskflow_submit` 提交真实结果；失败要写 `status="failed"`。只能提交自己的卡，不能替他人验收或批准。提交结果后等待验收或返工。仅在整份计划验收收尾后安排、撰写及汇总心得。若本计划是一个项目阶段，还须等待整个项目总验收。收到符合上述条件的心得通知后，用 `taskflow_sleep_note` 提交自己的心得。

## 心得格式

执行者的 `taskflow_sleep_note.text` 和主理人的 `taskflow_sleep_consolidate.text` 默认使用下面三个 Markdown 二级标题。只有实际发生错误或弯路时，才在最后一段之前插入 `## 里面的错误怎么避免`，写明实际原因和预防办法。无实际错误时直接省略该标题及整段。

```markdown
## 做了什么
写本卡实际完成的工作，点明最有价值的产物或验证结果。

## 为什么这么做
选本卡一项关键判断，交代依据、取舍和核验方法。

## 要在下次任务中做的更好我需要什么
写下次要补的具体条件，或本次有证据支持、可复用的步骤。
```

提交时会比较同一计划里已保存的真实心得。收到 `note_duplicate` 时，按照自己的任务卡和独立证据重写，然后提交原卡。简单换词或调整标点无法提供新的经验。

主理分别汇总、去重，保留不同执行者的事实归属和不同需求；有真实错误时汇总错误及避免方法，所有来源均无错误时省略错误段。不将建议冒充已完成操作，不得编造错误、验证证据或需求。必填段缺失、已有段为空、标题重复或错序会被拒绝，拒绝时不会写入新心得或消费草稿。历史心得保留原文，不能为满足新格式补造历史事实。心得标题仍用 `title` 简短概括主题，正文仍写入原 `text` 字段，并沿现有关键词检索和技能晋升流程保存与导出。

## 约束

不得把聊天回复冒充工具提交；不得代群主批准确认门。测试门、确认门、依赖及重试上限均以宿主拒绝或接受结果为准。看板仅显示状态，写操作由群内 Bot 工具完成。
